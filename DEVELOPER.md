## 1. Что это за система

Заказчик — **АО «Казтелерадио»** (оператор телерадиовещания РК: АМС — антенно-мачтовые сооружения, РТС,
филиалы по областям). Система состоит из двух модулей на одном сервере, одной базе и одном входе:

| Модуль | Адрес | Для кого | Что делает |
|---|---|---|---|
| **CRM ОР ПСД** | `/` | Отдел разработки ПСД, канцелярия, филиалы, бухгалтерия, ОКО, техучёт, руководство, внешние Заказчики | Приём и проведение заявок на **ТУ** (технические условия), **ПСД** (проектно-сметная документация) и **СМР** (строительно-монтажные работы) по Регламенту; договоры и оплата; АВР; архив актов; сроки, эскалации, отчёты |
| **Портал допусков СУА** | `/dopusk/` | Сторонние организации (подрядчики, арендаторы), Служба управления активами, филиалы | Заявка на допуск персонала и техники на объект, проверка основания, согласование филиалом, электронный допуск с кодом, проверка на объекте |

Главная особенность: **система реализует утверждённый Регламент ОРПСД-Р-01 ред. 2**. Этапы, сроки, условия
переходов и автоматические действия — это пункты Регламента, и в коде у них стоят ссылки на эти пункты
(`regulationRef: 'п. 86'`). Сервер не даёт нарушить условие Регламента даже прямым вызовом API. Портал
допусков точно так же реализует **Инструкцию о допуске сторонних организаций**.

Второй сквозной принцип — **нет «ничьих» карточек**: у каждой заявки, поручения, служебной записки,
документа на визу, запроса в реестр и заявки на допуск всегда есть конкретный исполнитель (п. 102
Регламента). Подробно — раздел 8.

Чего в системе нет и делать не нужно: **интеграции с 1С** (решение заказчика — счета, АВР, ЭСФ отмечаются
вручную), электронной подписи (отметка «завизировано» — не ЭЦП), офлайн-режима и QR-сканера на объекте.

## 3. Быстрый старт на своём компьютере

Нужны: **Node.js 22.6+**, **Docker** (только для PostgreSQL), git. Сборки нет — TypeScript исполняется
Node.js напрямую.

### 3.1. База

```bash
docker run -d --name qtr-pg-test -e POSTGRES_PASSWORD=testpass -e POSTGRES_USER=qtr -e POSTGRES_DB=qtr_crm_ui -p 55432:5432 postgres:16-alpine
```

Эта же база используется и для сквозных тестов (там отдельная база `qtr_crm_test`, см. раздел 16).

### 3.2. Настройки

```bash
npm ci
```

Создайте файл `.env.local` (в git не попадает — шаблон `.env.*` в `.gitignore`):

```ini
PORT=3000
DATABASE_URL=postgres://qtr:testpass@127.0.0.1:55432/qtr_crm_ui
# Без входа — от имени этой учётной записи (только разработка). Уберите строку, чтобы проверять настоящий вход.
DEV_LOGIN_EMAIL=dev-admin@qtr.kz
DEV_LOGIN_NAME=Разработчик
BOOTSTRAP_ADMIN_EMAIL=dev-admin@qtr.kz
STORAGE_ROOT=./storage
JOBS_ENABLED=false
MIGRATE_ON_START=true
# openssl rand -hex 32 — без него сервер не стартует
AUTH_SECRET=замените-на-64-hex-символа
COOKIE_SECURE=false
```

### 3.3. Запуск

```bash
npm run local
```

Откройте `http://localhost:3000/` (модуль ОР ПСД) и `http://localhost:3000/dopusk/` (допуски). При первом
запросе `dev-admin@qtr.kz` станет администратором (`BOOTSTRAP_ADMIN_EMAIL`), миграции применятся сами
(`MIGRATE_ON_START=true`).

Справочники (филиалы, объекты, прейскурант, контрагенты) — вымышленные:

```bash
npm run seed:demo
```

Чтобы посмотреть систему под другой ролью, поменяйте `DEV_LOGIN_EMAIL` на адрес пользователя с нужной
ролью (заведите его на экране «Пользователи») и перезапустите сервер.

### 3.4. Демонстрационный стенд — всё сразу

На **пустой** базе можно развернуть стенд: 22 учётные записи всех ролей и 16 заявок во всех ключевых
состояниях, проведённых через настоящий API.

```bash
docker exec qtr-pg-test createdb -U qtr qtr_crm_demo
```

```bash
DATABASE_URL=postgres://qtr:testpass@127.0.0.1:55432/qtr_crm_demo npm run migrate
```

```bash
DATABASE_URL=postgres://qtr:testpass@127.0.0.1:55432/qtr_crm_demo npm run seed:demo
```

```bash
DATABASE_URL=postgres://qtr:testpass@127.0.0.1:55432/qtr_crm_demo STORAGE_ROOT=./storage-demo npm run seed:scenario
```

Сервер стенда запускается с `DEMO_MODE=true` и `DEMO_PASSWORD=demo-stand-2026` (без `DEV_LOGIN_EMAIL`):
страница входа покажет список учётных записей, а код входа — прямо на экране. Сценарий привязан к датам:
**пересоздавайте стенд накануне показа**. Сценарий показа — `docs/Демо_стенд.md`.

### 3.5. Режим наблюдения

```bash
npm run dev
```

Перезапускает сервер при изменении файлов в `src/` (переменные окружения задайте сами или используйте
`npm run local` и перезапускайте вручную). Интерфейс (`design/`) отдаётся с диска без кэша — достаточно
обновить страницу.

## 4. Стек и принципы

| Что | Выбор | Почему |
|---|---|---|
| Язык | TypeScript, исполняется `node --experimental-strip-types` | Нет шага сборки — проще развёртывать в закрытом контуре |
| Сервер | Свой роутер на `node:http` (`src/server/http.ts`) | Без веб-фреймворков: меньше зависимостей для обновления |
| База | PostgreSQL 16, драйвер `pg`, SQL руками | Без ORM: запросы видны, схема в миграциях |
| Почта | `nodemailer` | Единственная зависимость кроме `pg` |
| Интерфейс | Ванильный JS + HTML + CSS, без сборщика и фреймворка | Файлы отдаются как есть; правка — обновить страницу |
| Тесты | Встроенный `node:test` | Без Jest/Mocha |

Зависимостей в `package.json` всего две: `pg` и `nodemailer`. **Не добавляйте зависимости без серьёзной
причины** — система ставится на сервер Общества, каждая библиотека — это обновления и проверка СБ.

**Ограничения strip-types.** Node.js только вырезает типы, поэтому нельзя использовать то, что требует
транспиляции: `enum`, `namespace`, параметры-свойства в конструкторе (`constructor(private x)`),
декораторы. Импорты пишутся **с расширением `.ts`**, а импорт только типов — через `import type`.
Проверки типов при запуске нет; при желании подключите `tsc --noEmit` локально (в репозитории не настроено).

**Язык.** Интерфейс, сообщения об ошибках, комментарии и коммиты — на русском. Идентификаторы — на
английском. Сообщения об ошибках пишутся для пользователя: что не так и что сделать.

## 5. Архитектура

```
 Браузер ──► nginx (TLS, лимиты, стирает X-QTR-*) ──► Node.js-процесс (127.0.0.1:3000) ──► PostgreSQL
                                                         │                                  ▲
                                                         ├─ статика design/                 │
                                                         ├─ API /api/v1/…                   │
                                                         ├─ фоновые задания (таймер) ───────┤
                                                         └─ файлы актов ─► STORAGE_ROOT     │
                                                                          ClamAV (по желанию)
```

Один процесс отдаёт и интерфейс, и API, и раз в `JOBS_INTERVAL_MINUTES` выполняет фоновые задания
(эскалации, напоминания, отправку почты из очереди).

### Слои

```
design/              интерфейс: обращается только к API через design/api.js
   │
src/server/          HTTP: маршруты, вход, права, проверка ввода, журнал, письма
src/permits/server/  то же для допусков
   │
src/process/         процессный движок ОР ПСД: этапы, переходы, условия, сроки, правила, фоновые задания
src/permits/domain/  правила Инструкции о допуске (чистые функции)
src/domain/          календарь и сроки, проверка заявки, расчёт стоимости, типы
   │
src/db/              SQL: репозитории, миграции, назначение исполнителей
src/storage/         файлы и антивирус
```

**Ключевое правило:** `src/process/engine.ts`, `transitions.ts`, `src/domain/*` и
`src/permits/domain/*` — **чистые функции без базы и HTTP**. Они получают снимок данных и возвращают
решение. Поэтому правила Регламента покрываются быстрыми модульными тестами, а маршруты только собирают
снимок, вызывают движок и записывают результат в транзакции.

### Путь запроса на примере перехода по этапу

`POST /api/v1/requests/:id/transition` ([src/server/app.ts](src/server/app.ts), обработчик `transition`):

1. `guardOrigin` — изменяющий запрос принимается только со своего сайта (`Origin` = `APP_ORIGIN`).
2. `currentActor` — пользователь по cookie сессии (или dev-учётке / заголовкам прокси).
3. `rbac.require(actor, 'request.transition')` — право вообще делать переходы.
4. `loadVisible` — заявка в области видимости пользователя, иначе 404.
5. Проверка, что роль пользователя названа в определении перехода (`TRANSITIONS[].roles`); отказ пишется
   в журнал.
6. Сервер сам вычисляет факты, которые нельзя доверить клиенту (истекла ли оферта, прошёл ли срок
   замечаний к АВР).
7. `applyTransition(...)` из движка — проверка условий Регламента; нарушение →
   `422 regulation_violation` со списком `failures` и ссылками на пункты.
8. В одной транзакции `db.tx`: смена этапа с **оптимистичной блокировкой по `version`** (409, если
   карточку успели изменить), закрытие старой и открытие новой записи `request_stages`, назначение
   исполнителя, журнал, побочные действия (поручения, договоры).
9. После транзакции — письма в очередь (`notifyTransition`).

Изменить `stage_code` заявки можно **только** так. Других маршрутов, пишущих этап, нет — сохраняйте это.

### `src/server/` — HTTP

|---|---|

## 7. Процесс заявки ОР ПСД

### Этапы (`src/process/stages.ts`)

```
draft → registered → tv_review → offer → awaiting_payment ─┬─► tu ──┬─► psd ──┬─► smr_prep → smr → avr → closing → closed_done
 Заказчик  канцелярия   ОР ПСД     ОР ПСД   Заказчик        │        │         │    (оборудование)  (филиал) (бухгалтерия)
                                                            ├─► psd  ├─► avr   ├─► offer (КП на СМР после ПСД)
                                                            └─► smr_prep        └─► avr
Конечные: closed_done · closed_rejected (отказ, нет ТВ) · closed_expired (истекла оферта) · closed_cancelled (расторжение)
```

У каждого этапа: норматив (`slaValue` + `slaUnit`: рабочие/календарные дни, операционный день, в день
поступления), сторона-владелец (`customer`, `records`, `orpsd`, `branch`, `accounting`), статус, который
видит Заказчик (7 статусов ТЗ №10), и ссылка на пункт. Этап с `serviceScope` применяется, только если в
заявке есть эта услуга.

Нормативы ДИТ может изменить на экране «Этапы и сроки» с основанием (таблица `stage_sla_overrides`); при
старте `loadStageOverrides` накладывает их на определения из кода.

### Переходы и условия (`src/process/transitions.ts`)

Каждый переход — запись `{ from, to, title, guard, regulationRef, roles }`. `guard` получает
`RequestSnapshot` (этап, услуги, ТВ, договоры с датами оплаты, флаги сметы и т. д.) и возвращает список
невыполненных условий. Примеры:

- работы по услуге — только после 100 % оплаты **договора этой услуги** (п. 86): оплата ПСД не открывает СМР;
- договор на СМР — не раньше утверждения сметы (п. 53);
- СМР — только после завизированного акта приёма-передачи оборудования (п. 58);
- КП — только при подтверждённой ТВ с версией мастер-файла (пп. 16.3, 16.5);
- закрытие по оферте — только если срок действительно истёк (это определяет сервер, не клиент).

Интерфейс получает список доступных переходов вместе с карточкой (`GET /requests/:id`) и показывает
невыполненные условия с пунктами. Но проверка **всегда** повторяется на сервере.

### Подача и регистрация

При подаче (`POST /requests` или переход `draft → registered`) система сама присваивает номер
`ЗК-ГГГГ-NNNN`, регистрационный номер и дату. Канцелярия проверяет и **подтверждает** регистрацию одной
кнопкой (`registered → tv_review`), после чего заявка уходит в ОР ПСД, а филиалу — письмо (п. 6).

### Замечания и возврат

`POST /requests/:id/remarks` — возврат на доработку с замечаниями к полям (ТЗ №11). Заказчик правит только
поля с замечаниями (`PATCH`), замечание снимается автоматически при исправлении поля; повторная отправка
(`resubmit`) возможна, только когда открытых замечаний нет.

### Сроки и эскалации

`request_stages` хранит историю: вход, выход, срок (`due_at`), продление с основанием, уровень эскалации,
признак нарушения. Это основа «Узких мест» и отчётов. Эскалацию выполняет фоновое задание (раздел 12).

## 8. Исполнители — у каждой карточки есть человек

Это **основной принцип системы** (п. 102 Регламента, решение заказчика 29.09.2026). Не вводите
состояний «никому не назначено».

- У заявки два исполнителя: **ответственный ОР ПСД** (`requests.assignee_id`) ведёт её от подачи до
  закрытия; **исполнитель этапа** (`request_stages.assignee_id`) — кто действует сейчас (канцелярия,
  ОР ПСД, филиал, бухгалтерия). На этапах Заказчика исполнитель — ответственный ОР ПСД: он контролирует срок.
- Исполнитель назначается **в той же транзакции**, что и переход (`assignMissing`).
- Не выбран конкретный человек — `src/db/executors.ts` берёт наименее загруженного сотрудника
  подразделения (для филиала — своего); в филиале без пользователей — главного инженера области, затем
  курирующего заместителя (Приложение 7). Отсутствующие (`user_absences`) не назначаются, их задачи видит
  замещающий.
- Тот же принцип — у документа на визу, запроса изменения реестра, заявки на допуск, служебной записки,
  поручения.
- Страховка: задание `runExecutorCheck` в каждом проходе назначает недостающих и заменяет отключённых;
  если назначить некого — письмо ДИТ и ОР ПСД.
- Всё, что лежит на человеке, видно на экране «Мои задачи» (`src/server/tasks.ts`); руководитель
  (`users.is_head`) видит нагрузку команды.

Добавляете новый вид рабочего объекта — добавьте ему исполнителя, подбор в `executors.ts`, проверку в
`runExecutorCheck` и строку в `tasks.ts`.

## 9. Роли, права и области видимости

Роли (`src/domain/types.ts`): `admin` (ДИТ), `records` (канцелярия), `orpsd`, `branch` (филиал), `oko`,
`assets` (техучёт), `accounting`, `management`, `customer` (Заказчик), `contractor` (подрядчик в
допусках), `permits` (СУА), `auditor` (СБ — только журнал).

Права — матрица `MATRIX` в [src/server/rbac.ts](src/server/rbac.ts). Принцип: **запрещено всё, что явно не
разрешено**. В маршруте право проверяется вызовом `rbac.require(actor, 'permission')`.

Области видимости заявок (`requestScope`): admin — все; Заказчик — только своей организации; пользователь
только с ролью «Филиал» — заявки на объекты своего филиала; остальные с `request.view` — все.

**Внешние роли не совмещаются.** `customer` и `contractor` назначаются только поодиночке, без других
ролей — это проверяет сервер (`users.ts`) и триггер в базе (миграция 008). Организация, работающая в обоих
кабинетах, имеет разные учётные записи.

**Заказчику не отдаётся внутренняя кухня**: журнал с именами сотрудников, служебные записки, расчёты ТВ,
эскалации. Это вырезает сервер (`src/server/customer.ts`), а не только интерфейс. Добавляя поле в
карточку, решите, должен ли его видеть Заказчик.

Роли назначает только ДИТ вручную (экран «Пользователи»). Подрядчика и представителя уже известной
организации при самостоятельной регистрации подтверждает ДИТ.

## 10. Вход и сессии

Всё в [src/server/login.ts](src/server/login.ts), страница [design/login.html](design/login.html).

- Почта + пароль, затем 6-значный код на почту (10 минут, 5 попыток, одноразовый). В базе — только
  свёртки: пароль — scrypt (`passwords.ts`), код — HMAC с `AUTH_SECRET`, ключ сессии — SHA-256.
- Сессия — cookie `qtr_session` (HttpOnly, Secure, SameSite=Lax), 30 минут бездействия, не более 12 часов.
- Блокировка после 10 неверных паролей на 15 минут; ограничение частоты по адресу и по почте; одинаковые
  ответы для существующей и несуществующей почты.
- Письма с кодами и ссылками отправляются **сразу**, минуя очередь. При выключенной почте
  (`SMTP_ENABLED=false`) они печатаются в консоль сервера — так удобно разрабатывать с настоящим входом.
- `DEV_LOGIN_EMAIL` — вход без пароля от имени указанного адреса. Сервер **отказывается стартовать** с ним
  при `NODE_ENV=production`.
- `DEMO_MODE=true` — код входа показывается на экране. Только для стенда с вымышленными данными.
- `SSO_ENABLED` — опционально: личность от oauth2-proxy через заголовки `X-QTR-*` с общим секретом
  (`auth.ts`). Сейчас не используется.

Текущий пользователь определяется в `currentActor` ([src/server/app.ts](src/server/app.ts)): сессия →
заголовки прокси → dev-учётка.

### Журнал действий

Таблица `events` — журнал всех действий (кто, что, когда, IP, результат, пункт Регламента). Запись —
`repo.logEvent(...)`. Журнал **неизменяем**: триггер `trg_events_immutable` запрещает UPDATE/DELETE, а
роль приложения `qtr_app` (`deploy/db-app-role.sql`) не имеет на это прав. Тесты очищают журнал, включая в
транзакции `set_config('qtr.audit_purge', 'on', true)` — в коде приложения так не делайте.

### Доступ к базе из кода

```ts
const rows = await db.query<{ id: string }>(`SELECT id FROM users WHERE email = $1`, [email]);
const one  = await db.one<{ n: number }>(`SELECT count(*)::int AS n FROM requests`);
await db.tx(async (t) => { /* всё через t — откатится целиком при исключении */ });
```

Только параметризованные запросы (`$1`), никакой склейки строк с вводом пользователя. Внутри `tx`
передавайте в функции репозитория `t`, а не `db`.

## 12. Фоновые задания и уведомления

`runAllJobs` в [src/process/scheduler.ts](src/process/scheduler.ts) вызывается таймером в `index.ts` (или
`npm run jobs` из cron). Задания: исполнители (п. 102), эскалации (п. 100), закрытие по оферте, приёмка по
молчанию (пп. 94–95), напоминания об оборудовании, истечение ТУ и проекта, отчёты филиалов, контрольные
точки и продление ПСД, напоминание об оплате, АВР и ЭСФ, годовой отчёт, задания допусков
(`src/permits/jobs.ts`).

Требования к заданию:

- **идемпотентность** — проход повторяется каждые 15 минут; повторную отправку предотвращает
  `alreadySent` (проверка по ключу события в `notifications`);
- возвращает `{ job, regulationRef, affected }`;
- ошибка одного прохода не роняет процесс.

При нескольких экземплярах приложения задания включают только на одном (`JOBS_ENABLED=false` на остальных).

**Письма** не отправляются из обработчиков напрямую: `notify`/`enqueue` кладут их в таблицу
`notifications`, а `processQueue` отправляет (до 5 попыток, затем «сбой» — ДИТ видит и повторяет на экране
«Эскалации и уведомления»). Исключение — коды входа и ссылки (сразу). Каждое письмо пользователю
дублируется в «колокольчик» (`inbox`) и замещающему. Правило автоматизации, выключенное ДИТ, писем не
рассылает, но действие выполняется и пишется в журнал. Тексты можно переопределить шаблонами
(`mail_templates`, экран в интерфейсе).

## 13. Файлы и антивирус

`FileStore` ([src/storage/files.ts](src/storage/files.ts)) хранит файлы в `STORAGE_ROOT`; в базе — карточка,
ключ и SHA-256 (`file_versions`). Разрешены PDF, PNG, JPG, DOCX, XLSX и ZIP; тип проверяется по сигнатуре,
а не по расширению, исполняемые файлы не принимаются. При `ANTIVIRUS=clamd` файл до записи проверяется демоном ClamAV по протоколу INSTREAM;
антивирус недоступен — `503`, непроверенный файл не сохраняется. Каждое скачивание пишется в журнал.

Резервная копия базы без копии `STORAGE_ROOT` бесполезна.

## 14. Портал допусков СУА

Отдельный модуль той же системы: `src/permits/`, интерфейс `design/dopusk/`, API `/api/v1/permits/…`.
Соответствие пунктам Инструкции — `docs/Допуски_соответствие_Инструкции.md`.

Статусы заявки на допуск: `draft → pending_review → approved | rejected`, а также `withdrawn` (отозвана
организацией), `revoked` (отозван допуск), `closed` (работы завершены).

Как устроено:

- подрядчик (`contractor`) ведёт своих работников (Приложение 1, удостоверения, паспорта, визы), транспорт и
  бригады и видит только свою организацию;
- цель работ определяет допустимое основание (`domain/rules.ts`); основание проверяется по данным модуля
  ОР ПСД, архива актов и реестра договоров аренды. Режим проверки (мягкий — скан и ручное подтверждение, или
  строгий) — настройка `/permits/settings`;
- согласование руководства филиала нужно для АМС, изысканий, более 5 человек, ночи (22:00–06:00) и
  выходных, аварий;
- СУА рассматривает за 14 рабочих дней; одобрение выдаёт электронный допуск с кодом проверки и копией
  в филиал; аварийный допуск — сразу, письменное оформление досылается за 2 дня;
- филиал на объекте проверяет допуск по коду, ИИН или фамилии и отмечает инструктаж и СИЗ (`site_admissions`).

Толкования Инструкции, принятые разработкой (подлежат подтверждению СУА), перечислены в
`docs/Что_осталось_сделать.md` §3.3 и `docs/Решения_по_открытым_вопросам.md`. Инструкция **ещё не
утверждена** — правила могут поменяться, держите их в `domain/rules.ts` и настройках, а не в маршрутах.

## 15. Интерфейс

- **Без сборки и фреймворка.** Сервер отдаёт `design/` как статику. Экраны рисуются функциями, которые
  возвращают HTML-строки; всё пользовательское содержимое экранируется функцией `esc()` из `shell.js` —
  не вставляйте данные в разметку без неё.
- **Все запросы — через `design/api.js`.** Он разбирает ошибки: `fields` подсвечивает поля формы,
  `failures` выводятся дословно со ссылками на пункты Регламента, 409 — «обновите карточку».
- **Меню и кнопки — по правам**, которые приходят в `GET /api/v1/me` (`permissions`). Видимость экранов —
  `VIEW_PERMISSION` и `viewAllowed` в `index.html`. Но скрыть кнопку — не защита: право проверяет сервер.
- **Адреса.** Экран и открытая карточка пишутся в hash: `#/board`, `#/registry/ЗК-2026-0001`; в портале
  допусков — `ЗД-…`. Работают «Назад», обновление и ссылки из писем (`/#ЗК-…`).
- **Режимы `index.html`.** Рабочий (сервер доступен), демонстрационный (файл открыт с диска — встроенные
  примеры из `demo-data.js`), «нет доступа» (сервер отказал — примеры **не** показываются).
- **Конфигурация процесса** для интерфейса — `design/config.js`, генерируется из `src/process`. Изменили
  этапы, переходы или правила — выполните `npm run design:config` (и `npm run seed:sql`).
- **Доступность и телефон.** Цвета — токены в `shell.css` с контрастом WCAG AA, минимальный шрифт 11.5px,
  `focus-visible`, элементы управления 40px; таблицы для внешних пользователей на телефоне превращаются в
  карточки (`table.stack-sm`). Сохраняйте это при правках.
- «Справка» и приветствие при первом входе — тексты по ролям в `shell.js` (`HELP`).

## 17. Типовые задачи — как сделать

### Новый маршрут API

1. Выберите модуль в `src/server/` по разделу (или создайте `xxx.ts` с функцией
   `registerXxxRoutes(router, deps: RouteDeps)` и вызовите её в `createApp`).
2. В обработчике: для изменяющих запросов — `deps.guardOrigin(ctx)`; затем `const actor = await
   deps.actor(ctx)`; `rbac.require(actor, '…')`; заявку брать через `deps.loadVisible(actor, id)`.
3. Ошибки — только `ApiError` (`badRequest` с `fields`, `forbidden`, `notFound`, `conflict`).
4. Изменение данных — в `db.tx`, с `repo.logEvent({...deps.audit(ctx, actor), action, entity, entityId,
   regulationRef})`.
5. Письма — `notify(...)` после транзакции.
6. Тест: модульный для логики, сквозной для маршрута. Строку в таблицу API в README.

### Изменить норматив, этап, переход или условие

1. Правка в `src/process/stages.ts` / `transitions.ts` (условие — функция-guard со ссылкой на пункт).
2. `npm run seed:sql` и `npm run design:config`.
3. Тест в `tests/process.test.ts`.
4. Если меняется только срок — его может поменять ДИТ в интерфейсе, код не нужен.

### Новое правило автоматизации или фоновое задание

1. Правило — в `src/process/rules.ts` (id, событие, действие, пункт), затем `npm run seed:sql` и
   `design:config`.
2. Задание — функция `runXxx(db, calendar)` в `scheduler.ts` (или `permits/jobs.ts`), идемпотентная,
   добавить в `runAllJobs`.
3. Письма — через `notify` с `ruleId`, чтобы выключение правила останавливало рассылку.

### Новая таблица или поле

1. Новая миграция `src/db/014_….sql` (комментарий в начале: зачем и какой пункт).
2. Код репозитория в `src/db/`. Если таблица ссылается на пользователей — добавьте её в очистку в
   сквозных тестах (`PERMIT_TABLES` и аналогичные списки в `tests/*.integration.test.ts`).
3. Если в таблице есть «ответственный» — см. раздел 8.

### Новая роль или право

1. `Role` и `ROLE_NAME` в `src/domain/types.ts`; права в `MATRIX` (`rbac.ts`).
2. Ограничение `user_roles.role` в базе — новой миграцией.
3. Роль в форме пользователя и справка в `shell.js` (`HELP`).

### Новый экран интерфейса

1. Пункт в `MENU*` и `TITLES`, право в `VIEW_PERMISSION` (`design/index.html`).
2. Функция отрисовки и ветка в `render()`.
3. Данные — через `api.js`. Проверка на ширине телефона.

## 18. Соглашения в коде

- **Ссылка на норму.** Каждое бизнес-правило сопровождается ссылкой на пункт Регламента, ТЗ или
  Инструкции — в комментарии, в `regulationRef` и в тексте ошибки. Без ссылки правило нельзя проверить.
- **Комментарий объясняет «почему»**, а не «что»: какое требование, какое решение, какой случай
  предотвращает. Стиль — как в существующих файлах (шапка модуля с назначением и источниками).
- **Сервер — источник истины.** Даты, сроки, номера, факты истечения вычисляет сервер; клиенту не
  доверяем ни права, ни этап, ни даты.
- **Оптимистичная блокировка.** Изменения карточки передают `version`; несовпадение — `409`.
- **Журнал** у каждого изменяющего действия и у каждого отказа по правам или Регламенту.
- **Даты** — строки `YYYY-MM-DD` в часовом поясе Алматы (`today()` из `calendar.ts`), не `new Date()`
  напрямую.
- **Персональные данные** не выходят за пределы сервера, не пишутся в URL и логи.
- **Коммиты** — на русском, в стиле `feat: …`, `fix: …`, `feat(ui): …`.

# CRM ОР ПСД — АО «Казтелерадио»

Приём и обработка заявок на выдачу технических условий, разработку проектно-сметной
документации и выполнение строительно-монтажных работ; архив актов; контроль сроков
и показатели загрузки.

Система реализует действующий **Регламент оказания услуг ОРПСД-Р-01 ред. 2**: нормативы
этапов, условия переходов и правила автоматизации хранятся со ссылками на пункты и
проверяются на сервере. Обойти условие Регламента, обратившись к API напрямую, нельзя.

Второй модуль той же системы — **портал допусков СУА** (`/dopusk/`): допуск персонала и техники
сторонних организаций на объекты по Инструкции о допуске.

| Кому | Что читать |
|---|---|
| Разработчику | **[DEVELOPER.md](DEVELOPER.md)** — устройство, карта кода, локальный запуск, типовые задачи, подводные камни |
| ДИТ — установка и эксплуатация | этот файл |
| Пользователям | `docs/Руководство_пользователя.md` (проектная документация, см. ниже) |

**Состояние на 06.10.2026:** версия для показа готова, запуск — 15.10.2026. Модульных тестов 163,
сквозных 154 — все проходят.

## Требования к серверу

Подробно — ресурсы, разметка дисков, сеть, резервное копирование и что предоставляет ДИТ —
в `docs/Требования_к_серверу.md`. Кратко: Ubuntu Server 24.04 LTS, 4 vCPU, 8 ГБ ОЗУ, SSD.

- Linux, **Node.js 22.6+** и **PostgreSQL 16+**;
- nginx как обратный прокси;
- доменное имя и TLS-сертификат;
- почтовый сервер (SMTP): коды входа и ссылки на пароль приходят письмом;
- исходящий доступ к реестру npm на время установки.

Корпоративный провайдер входа (OIDC) не нужен: учётные записи и вход — в самой
системе. Подключить его можно позже, см. «Как устроен вход».

**Docker не обязателен.** Приложение — обычный процесс Node.js, работающий с
PostgreSQL. Ниже два пути установки: без контейнеров (systemd) и через Docker
Compose. Они равноценны, выбирайте привычный для вашей ИТ-службы.

Все данные остаются на сервере Общества. Персональные данные и коммерческая тайна
(реестр АМС, загрузка, арендаторы) за пределы контура не передаются.

## Переменные окружения

Настройки задаются в файле `.env` (копируется из `.env.example`, в репозиторий
не коммитится). Обязательные:

| Переменная | Как получить |
|---|---|
| `APP_ORIGIN` | внешний адрес системы, например `https://crm.example.kz` |
| `SERVER_NAME` | домен без схемы, например `crm.example.kz` |
| `DATABASE_URL` | строка подключения; нужна при установке без Docker |
| `PGPASSWORD` | пароль базы: `openssl rand -base64 24` (используется в Compose) |
| `AUTH_SECRET` | `openssl rand -hex 32` — не короче 32 символов; без него приложение не запускается |
| `SMTP_*` | почтовый сервер для кодов входа и уведомлений (см. «Фоновые задания и уведомления») |
| `BOOTSTRAP_ADMIN_EMAIL` | рабочая почта первого администратора ДИТ |

`DEV_LOGIN_EMAIL` на сервере не задаётся никогда: при `NODE_ENV=production` приложение с ним не запустится.

`DEMO_MODE=true` — только для демонстрационного стенда на вымышленных данных: код входа показывается на
экране (второго фактора нет), на каждой странице — жёлтая полоса «Демонстрационный стенд». `DEMO_PASSWORD` —
общий пароль учётных записей `npm run seed:scenario`, страница входа показывает его вместе со списком.

## Установка без Docker (systemd)

### 1. Подготовить сервер

```bash
sudo apt update
sudo apt install -y nodejs npm postgresql nginx
node --version     # должно быть 22.6 или новее
```

Если в репозитории дистрибутива Node.js старее 22.6, поставьте из NodeSource
либо распакуйте официальную сборку в `/usr/local`.

### 2. Создать пользователя и базу

```bash
sudo adduser --system --group --home /opt/qtr-crm qtrcrm

sudo -u postgres psql <<'SQL'
CREATE USER qtr WITH PASSWORD 'задайте-пароль';
CREATE DATABASE qtr_crm OWNER qtr;
SQL
```

### 3. Забрать код

```bash
sudo git clone <адрес-репозитория> /opt/qtr-crm
sudo chown -R qtrcrm:qtrcrm /opt/qtr-crm
cd /opt/qtr-crm
sudo -u qtrcrm npm ci --omit=dev
```

### 4. Настроить

```bash
sudo -u qtrcrm cp .env.example .env
sudo -u qtrcrm nano .env
sudo chmod 600 .env
```

Для установки без Docker нужна строка подключения целиком:

```
DATABASE_URL=postgres://qtr:пароль@localhost:5432/qtr_crm
```

### 5. Применить миграции и запустить службу

```bash
sudo -u qtrcrm npm run migrate

sudo cp deploy/qtr-crm.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now qtr-crm
systemctl status qtr-crm
```

### 6. Настроить nginx

```bash
sudo cp deploy/nginx-site.conf /etc/nginx/sites-available/qtr-crm
sudo nano /etc/nginx/sites-available/qtr-crm   # домен
sudo ln -s /etc/nginx/sites-available/qtr-crm /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
```

Проверка:

```bash
curl -fsS https://<домен>/api/v1/health
```

### Обновление

```bash
cd /opt/qtr-crm
sudo -u qtrcrm git pull
sudo -u qtrcrm npm ci --omit=dev
sudo -u qtrcrm npm run migrate
sudo systemctl restart qtr-crm
```

## Установка через Docker Compose

Тот же результат одной командой: база, приложение и nginx
поднимаются вместе с уже связанными сетями. Требуется Docker 24+ и Compose v2.

### 1. Забрать код на сервер

```bash
git clone <адрес-репозитория> /opt/qtr-crm
cd /opt/qtr-crm
```

### 2. Заполнить настройки

```bash
cp .env.example .env
```

Значения — в разделе «Переменные окружения» выше.

### 3. Положить сертификаты

```bash
mkdir -p deploy/certs
cp /путь/fullchain.pem deploy/certs/
cp /путь/privkey.pem  deploy/certs/
chmod 600 deploy/certs/privkey.pem
```

### 4. Запустить

```bash
docker compose up -d --build
docker compose exec app npm run migrate
```

Проверка:

```bash
curl -fsS https://$SERVER_NAME/api/v1/health
```

### 5. Роль базы для приложения (рекомендуется)

Чтобы приложение не могло менять схему и журнал действий, создайте роль `qtr_app`, впишите её пароль в
`APP_DB_PASSWORD` в `.env` и перезапустите приложение:

```bash
docker compose exec -T db psql -U "$PGUSER" -d "$PGDATABASE" -v app_password="'ПАРОЛЬ'" < deploy/db-app-role.sql
docker compose up -d app
```

Пока `APP_DB_PASSWORD` пуст, приложение работает под владельцем базы.

### 6. Обновление

```bash
cd /opt/qtr-crm
git pull
docker compose up -d --build
docker compose exec app npm run migrate
```

## Первый вход (любой способ установки)

1. Откройте `https://<домен>/login.html`, нажмите «Забыли пароль?» и введите адрес из
   `BOOTSTRAP_ADMIN_EMAIL`. Если администраторов ещё нет, учётная запись ДИТ создаётся,
   а на почту приходит ссылка для пароля.
2. Задайте пароль и войдите: почта, пароль, код из письма.
3. Сотрудников заведите на экране «Пользователи» (или импортом из CSV) и нажмите
   «Пригласить» — сотрудник сам задаст пароль по ссылке из письма.

Роли назначаются только вручную — самопроизвольной выдачи прав не происходит.
Пока почта не подключена (`SMTP_ENABLED=false`), письма со ссылками и кодами пишутся
в журнал службы: `journalctl -u qtr-crm -f` (или `docker compose logs -f app`).

Демонстрационные справочники (филиалы, объекты, прейскурант) — по желанию:

```bash
npm run seed:demo                        # без Docker
docker compose exec app npm run seed:demo  # в контейнерах
```

Демонстрационный стенд с заявками во всех состояниях — только на **пустой** базе, после `seed:demo`:

```bash
npm run seed:scenario                         # без Docker
docker compose exec app npm run seed:scenario # в контейнерах
```

Сценарий проводит 8 заявок ОР ПСД и 8 заявок на допуск через API приложения и заводит 22 учётные записи
(ОР ПСД, канцелярия, филиалы, СУА, Заказчики, подрядчики) с паролем `DEMO_PASSWORD` (по умолчанию
`demo-stand-2026`). Стенд запускается с `DEMO_MODE=true`. Сценарий показа — `docs/Демо_стенд.md`.

## Миграции и откат

Миграции повторно не применяются: каждый файл отмечается контрольной суммой.
Попытка изменить уже применённый файл прерывается с ошибкой — вместо правки
добавляйте новый файл. Исключение — файл конфигурации процесса `002_config.sql`:
он идемпотентен и переприменяется, когда меняются этапы или правила.

Откат кода:

```bash
git checkout <предыдущий-тег>
sudo systemctl restart qtr-crm        # либо docker compose up -d --build
```

Откат кода не откатывает схему базы. Перед обновлением снимайте резервную копию —
это единственный надёжный путь назад.

## Локальная разработка

Коротко (подробно, с файлом `.env.local` и демо-стендом — [DEVELOPER.md, раздел 3](DEVELOPER.md#3-быстрый-старт-на-своём-компьютере)):

```bash
docker run -d --name qtr-pg-test -e POSTGRES_PASSWORD=testpass -e POSTGRES_USER=qtr -e POSTGRES_DB=qtr_crm_ui -p 55432:5432 postgres:16-alpine
npm ci
npm run local      # настройки из .env.local, миграции при старте (MIGRATE_ON_START=true)
npm run seed:demo  # вымышленные справочники
```

`DEV_LOGIN_EMAIL` в `.env.local` — работа без входа от имени этой учётной записи (только разработка;
при `NODE_ENV=production` сервер не стартует). Без неё — настоящий вход; коды входа при выключенной
почте печатаются в консоль.

После правки этапов, переходов или правил в `src/process` пересоберите производные файлы:

```bash
npm run seed:sql && npm run design:config
```

## Как устроен вход

Одна схема для сотрудников, Заказчиков и подрядчиков (`src/server/login.ts`,
страница `design/login.html`): почта и пароль, затем одноразовый код на почту.

| Что | Как |
|---|---|
| Сотрудники | Заводит ДИТ на экране «Пользователи»; кнопка «Пригласить» присылает ссылку на первый пароль (72 часа, одноразовая) |
| Заказчики | Регистрируются сами: организация, БИН с проверкой контрольного разряда, ФИО, телефон, почта, пароль, согласие на обработку ПД; почта подтверждается кодом. Представителя уже известной организации подтверждает ДИТ — иначе любой, кто знает БИН, увидел бы чужие заявки. Выключается `AUTH_SELF_REGISTRATION=false` |
| Пароль | Не короче 10 символов, без распространённых и без адреса почты. Хранится только свёртка scrypt (N=32768) со случайной солью |
| Код входа | 6 цифр, 10 минут, 5 попыток, одноразовый; в базе — только HMAC-свёртка с `AUTH_SECRET`. Письмо уходит сразу, минуя очередь |
| Подбор | Ограничение частоты с адреса и на почту (приложение и nginx); после 10 неверных паролей вход блокируется на 15 минут; каждая попытка — в журнале |
| Перебор адресов | Вход, регистрация и восстановление отвечают одинаково для существующей и несуществующей почты |
| Сессия | Cookie `qtr_session`: `HttpOnly`, `Secure`, `SameSite=Lax`; в базе — SHA-256 ключа. 30 минут бездействия, не более 12 часов |
| Закрытие сессий | Выход; «выйти на всех устройствах»; смена пароля и отключение учётной записи закрывают все сессии сразу |
| Восстановление | Ссылка на 30 минут, одноразовая; после смены пароля — письмо владельцу |

Порт приложения наружу не публикуется: при установке через systemd оно слушает только
`127.0.0.1`, в Compose сеть `backend` помечена `internal`. nginx стирает служебные
заголовки `X-QTR-*`, пришедшие снаружи.

**Корпоративный вход (необязательно).** Если у Общества появится провайдер OIDC, его можно
подключить через oauth2-proxy: `SSO_ENABLED=true` и `AUTH_PROXY_SHARED_SECRET`. Приложение
тогда принимает и сессии, и личность от прокси; доверяет заголовкам только при совпадении
секрета.

## API

Базовый префикс `/api/v1`. Ответы — JSON, ошибки содержат `code`, а нарушения
Регламента — список `failures` со ссылками на пункты.

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/health` | Проверка доступности (без входа) |
| `GET` | `/config` | Этапы, переходы, правила, словари |
| `GET` | `/me` | Текущий пользователь, роли и права |
| `GET` | `/requests` | Список заявок в пределах прав; `executor=me` или id — «Мои заявки», `unassigned=1` — без исполнителя |
| `POST` | `/requests` | Подача заявки или сохранение черновика |
| `GET` | `/requests/:id` | Карточка: услуги, замечания, история, доступные переходы |
| `POST` | `/requests/:id/registration` | Исправление номера и даты регистрации канцелярией (п. 6). Номер и дату система присваивает сама при подаче; регистрацию канцелярия подтверждает переходом `registered → tv_review` — после этого письмо в филиал |
| `POST` | `/requests/:id/transition` | Переход по этапу — единственный способ сменить этап; исполнитель нового этапа назначается в том же действии |
| `GET` | `/requests/:id/executors` | Ответственный ОР ПСД, исполнитель этапа и кому их можно передать, с нагрузкой (п. 102) |
| `GET` | `/tasks`, `/tasks/count`, `/tasks/load` | «Мои задачи» (`?user=` — руководителям), число задач для значка, нагрузка сотрудников (ДИТ, ОР ПСД, ОКО, руководство) |
| `POST` | `/admin/import-requests` | Перенос действующих заявок из CSV: `apply: false` — предпросмотр с ошибками по строкам, `true` — запись (ДИТ) |
| `POST` | `/auth/register` | Самостоятельная регистрация Заказчика или подрядчика (`kind`) по БИН; подрядчика и представителя известной организации подтверждает ДИТ |
| `POST` | `/requests/:id/executor` | Передача заявки: `kind` = `responsible` (ОР ПСД) или `stage` (подразделение этапа), с причиной; журнал и письмо новому исполнителю |
| `POST` | `/requests/:id/tv` | Фиксация оценки ТВ с версией мастер-файла (п. 16.5) |
| `POST` | `/requests/:id/remarks` | Возврат на доработку с перечнем замечаний (ТЗ №11) |
| `PATCH` | `/requests/:id` | Исправление заявки: черновик — всегда, поданная — только по замечаниям; замечание к исправленному полю снимается (ТЗ №11) |
| `POST` | `/requests/:id/resubmit` | Повторная отправка исправленной заявки — только без открытых замечаний |
| `POST` | `/requests/:id/remarks/:remarkId/resolve` | Снятие замечания общего характера — ОР ПСД |
| `GET`/`POST` | `/requests/:id/contracts` | Договоры заявки; регистрация договора на услугу (пп. 21, 32, 48). На СМР — не ранее утверждения сметы (п. 53) |
| `POST` | `/contracts/:id/payment` | Фактическая дата поступления 100 % оплаты по договору (пп. 86, 88) |
| `POST` | `/contracts/:id/terminate` | Расторжение договора и сумма возврата (пп. 96–97) |
| `POST` | `/requests/:id/flags` | Смета, распоряжение, передача результата, направление АВР, приёмка и замечания Заказчика к АВР (пп. 41, 60, 24, 91, 94) |
| `POST` | `/requests/:id/extension` | Продление срока этапа с основанием; ПСД — не более 15 р.д. (пп. 33, 45) |
| `GET` | `/requests/:id/memos`, `/memos` | Служебные записки в филиал; филиал видит адресованные ему |
| `POST` | `/requests/:id/memos` | Запрос в филиал, срок ответа 3 рабочих дня (п. 10) |
| `POST` | `/memos/:id/answer` | Ответ филиала |
| `GET` | `/memos/stats` | Доля ответов филиалов в срок (п. 10) |
| `GET` | `/assignments` | Поручения по зарегистрированным заявкам (ТЗ №7, №8) |
| `GET` | `/assignments/export` | Выгрузка для ОКО в CSV (ТЗ, раздел 5) |
| `POST` | `/assignments/:id/accept` | Принятие поручения в работу — ОР ПСД |
| `POST` | `/assignments/:id/close` | Закрытие поручения с результатом — ОКО |
| `GET` | `/branches`, `/counterparties` | Справочники для формы пользователя |
| `POST` | `/users/:id/enable` | Включение отключённой учётной записи |

### Портал допусков (`/api/v1/permits`)

Модуль СУА по Инструкции о допуске сторонних организаций (`docs/Допуски_соответствие_Инструкции.md`):
заявка — официальный запрос организации с целью работ, основанием, периодом и временем, работниками по
Приложению 1 и подписанным сканом; рассмотрение СУА в течение 14 рабочих дней; согласование руководства
филиала (АМС, изыскания, более 5 человек, ночь и выходные, авария); аварийный порядок; электронный допуск с
кодом и копией в филиал; проверка на объекте (инструктаж, СИЗ); закрытие, отзыв, продление; реестр
договоров аренды. Подрядчик работает только со сведениями своей организации; СУА видит заявку с момента

## Интерфейс

Сервер отдаёт интерфейс сам: откройте `https://<домен>/` — загрузится
`design/index.html`, который обращается к API за данными. Отдельной сборки нет,
пересобирать при изменении экранов не нужно.

Один и тот же файл работает в двух режимах:

| Режим | Когда включается | Что видно |
|---|---|---|
| Рабочий | сервер доступен и учётная запись заведена | данные из базы, зелёная полоса «Рабочие данные» с именем и ролями |
| Демонстрационный | сервер недоступен (файл открыт прямо с диска) | встроенные примеры, жёлтая полоса «Демонстрационный режим» |
| Нет доступа | сервер ответил отказом | экран «Доступ к системе не предоставлен»; примеры не показываются, чтобы их не приняли за настоящие заявки |

Разделы меню и кнопки действий показываются по правам роли: сотрудник видит
только то, что ему разрешено, а условия перехода по Регламенту приходят с
сервера вместе с карточкой и выводятся со ссылками на пункты.

**Портал допусков** открывается отдельной ссылкой `https://<домен>/dopusk/` — это та же
система: тот же вход, те же учётные записи, оформление (`design/shell.css`, `design/shell.js`)
и клиент API. Настраивать nginx дополнительно не нужно. Роли назначает ДИТ на экране
«Пользователи»: «Подрядчик (допуски)» — представителю сторонней организации, с указанием
организации; «СУА · допуски» — специалисту Службы управления активами.

Кабинеты не пересекаются: Заказчик ОР ПСД не подаёт заявку на допуск, подрядчик — заявку на
услуги. Роли «Заказчик» и «Подрядчик» назначаются отдельно, без других ролей; это проверяет
сервер и ограничение в базе (миграция `008_external_roles.sql`). Если организация работает в
обоих кабинетах, у её представителей — разные учётные записи. Пользователь только с
ролью «Подрядчик» при входе на `/` сразу попадает на `/dopusk/`; у сотрудника с правами в обоих
модулях ссылка на другой модуль — в боковом меню.

Автономный файл для показа без сервера собирается отдельно:

```bash
npm run design      # design/prototype.html — один файл со встроенными примерами
```

## Фоновые задания и уведомления

Регламент требует действий по времени, а не только по действию пользователя.
Эти задания выполняются автоматически:

| Задание | Норма |
|---|---|
| Исполнитель у каждой открытой заявки, а также у документа на визу, запроса реестра, заявки на допуск и служебной записки: назначить недостающего, заменить отключённого; назначить некого — письмо ДИТ и ОР ПСД | п. 102 |
| Эскалация 1-го уровня в день нарушения срока, 2-го — через 2 рабочих дня; адресат не указан в справочнике филиала — исполнителю в ОР ПСД | п. 100 |
| Закрытие заявки по истечении срока оферты (10 рабочих дней) | табл. 1, п. 88 |
| Приёмка работ по молчанию Заказчика через 10 рабочих дней | пп. 94–95 |
| Напоминание о предоставлении оборудования за 10 дней до срока | пп. 55–57 |
| Уведомление об истечении срока действия ТУ и рабочего проекта | пп. 31, 47 |
| Напоминание о просроченном ответе филиала на служебную записку | п. 10 |
| Напоминание Заказчику об оплате за 3 рабочих дня до истечения оферты | п. 88 |
| Контрольная точка ПСД на 3-й рабочий день; предложение продлить ПСД за 5 дней до срока | пп. 33, 34.1 |
| Повторная оценка ТВ через 3 месяца после ПСД без оплаты СМР | п. 47 |
| Напоминание бухгалтерии: АВР и ЭСФ не оформлены через 1 операционный день | п. 91 |
| Напоминания об отчёте филиала (1–5 число) и сводном отчёте (с 20 февраля) | пп. 105, 109 |
| Допуски: просрочено рассмотрение (14 р.д.), не согласовано филиалом в срок, аварийный допуск не оформлен за 2 дня | Инструкция, пп. 14, 18 |
| Допуски: истекают удостоверения, паспорта, визы, договоры аренды (за 30 дней), допуск (за 3 дня) | Инструкция, пп. 13, 14, 19 |
| Допуски: согласующий или ответственный на объекте отключён — назначается другой | Инструкция, п. 20 |

Письма по ключевым событиям заявки (регистрация — филиалу, ответ о ТВ, договор и счёт,
оплата, начало работ, акт на визу, АВР, закрытие) ставятся в очередь в момент действия.

**Исполнители (п. 102).** У каждой поданной заявки — ответственный сотрудник ОР ПСД, который ведёт её
до закрытия, и исполнитель текущего этапа: канцелярия на регистрации, ОР ПСД на своих этапах, филиал заявки
на СМР, расчёты с контрагентами на АВР. На этапах Заказчика (оплата, оборудование, приёмка) исполнитель —
ответственный ОР ПСД: он контролирует срок. Не выбран конкретный человек — назначается наименее
загруженный сотрудник подразделения; в филиале без пользователей системы — главный инженер области, затем
курирующий заместитель директора (Приложение 7). Поручение ОКО без выбранного сотрудника получает
исполнителя так же. Передача пишется в журнал, новый исполнитель получает письмо.

Тот же принцип — у остальных рабочих объектов: документ на визу визирует ответственный ОР ПСД заявки,
запрос изменения реестра — конкретный специалист техучёта, заявку на допуск — специалист СУА, служебную
записку — главный инженер области либо сотрудник филиала. Всё, что лежит на человеке, — на экране
«Мои задачи»; руководитель видит нагрузку команды и задачи любого сотрудника.
Правило автоматизации, выключенное ДИТ на экране «Автоматизации», писем не рассылает.

По умолчанию задания выполняются внутри приложения каждые `JOBS_INTERVAL_MINUTES`
минут. При нескольких экземплярах приложения поставьте `JOBS_ENABLED=false` на всех,
кроме одного, либо выключите везде и запускайте по расписанию:

```bash
# /etc/cron.d/qtr-crm
*/15 * * * * qtrcrm cd /opt/qtr-crm && npm run jobs >> /var/log/qtr-crm-jobs.log 2>&1
```

Уведомления складываются в очередь в базе и отправляются отдельно. Пока
`SMTP_ENABLED=false`, сообщения копятся и не теряются; после включения почты
очередь разбирается. Неудачная отправка повторяется до пяти раз, затем помечается
сбойной и видна администратору в разделе «Эскалации и уведомления», где её можно
поставить на повторную отправку.

### Антивирусная проверка вложений

Без антивируса система проверяет тип, сигнатуру и размер файла. Чтобы проверять
и содержимое, подключите демон ClamAV (`clamd`) либо антивирус ДИТ, принимающий
протокол `INSTREAM`:

| Переменная | Значение |
|---|---|
| `ANTIVIRUS` | `clamd` — проверка включена; `off` — выключена (по умолчанию) |
| `CLAMD_HOST`, `CLAMD_PORT` | Адрес демона, по умолчанию `127.0.0.1:3310` |
| `CLAMD_TIMEOUT_MS` | Предельное время проверки одного файла, по умолчанию 30 000 |

Файл проверяется до записи в хранилище. Заражённый файл отклоняется, попытка
записывается в журнал как отказ. Если проверка включена, а антивирус недоступен,
загрузка откладывается с ответом `503`: непроверенный файл в архив не попадает.
Проверить подключение можно тестовым файлом EICAR — он должен быть отклонён.

## Резервное копирование

```bash
docker compose exec db pg_dump -U qtr -Fc qtr_crm > backups/qtr_$(date +%F).dump
```

Файлы актов лежат отдельно от базы и копируются отдельно:

```bash
tar -czf backups/files_$(date +%F).tar.gz -C /var/lib/qtr-crm storage
```

Восстановление на чистую базу:

```bash
docker compose exec -T db pg_restore -U qtr -d qtr_crm --clean --if-exists < backups/qtr_2026-09-22.dump
```

Копия базы без копии файлов бесполезна: в базе хранится только карточка документа
с ключом объекта и SHA-256, сам файл — в хранилище.

Рекомендуется схема 3-2-1: ежедневная копия, еженедельная полная, хранение копий

Сквозной работает против настоящей PostgreSQL:

```bash
docker run -d --name qtr-pg-test -e POSTGRES_PASSWORD=testpass -e POSTGRES_USER=qtr -e POSTGRES_DB=qtr_crm_test -p 55432:5432 postgres:16-alpine

DATABASE_URL=postgres://qtr:testpass@127.0.0.1:55432/qtr_crm_test npm run seed:demo
TEST_DATABASE_URL=postgres://qtr:testpass@127.0.0.1:55432/qtr_crm_test npm run test:integration
```

На 06.10.2026: модульных 163, сквозных 154 (ОР ПСД 112, допуски 31, вход 11). Сквозные тесты
**очищают таблицы** — `TEST_DATABASE_URL` должен указывать только на тестовую базу.

из PostgreSQL, проверка заявки, расчёт стоимости суммой позиций, условия переходов

заголовки, ролевая модель, маршрутизация, хранилище файлов и проверка сигнатур.

Портал допусков покрыт отдельно: модульно — основания по цели работ, мягкий и строгий режим,

## Границы текущего объёма

Реализовано: заявки на ТУ/ПСД/СМР с несколькими услугами в одной заявке, оценка
технической возможности с фиксацией версии реестра, этапы и сроки Регламента,
эскалация, замечания к полям, архив актов, показатели узких мест, журнал действий.

Требуют отдельного внедрения или решения:

- обмен с 1С и ИС ЭСФ — вне объёма; счета, АВР и ЭСФ отмечаются в системе вручную;
- электронная подпись: отметка «завизировано» подписью не является;
- модуль СУА «Портал допусков» (`/dopusk/`) — по Инструкции о допуске полностью; офлайн-режим проверки на
  объекте и сканирование QR-кода не делаются: допуск проверяется по коду с телефона;
- антивирусная проверка вложений реализована (ClamAV, `ANTIVIRUS=clamd`); включается после развёртывания демона;
- реестр АМС: расчёт ТВ, версии и запросы изменений работают; правка ярусов и
  загрузки — после решения, где ведётся реестр (вопрос 3 в ОР ПСД);
- публичная форма заявки без учётной записи (пожелание ОР ПСД) — ждёт решения; сейчас — кабинет Заказчика;
- из Регламента не реализованы раздел 15 (выездные проверки), раздел 9 и Прил. 9–10 (премирование),
  раздел 16 (реестр рисков), пп. 14, 110 (свободная ёмкость), плановые показатели п. 107;
- решения по открытым вопросам приняты и описаны в `docs/Решения_по_открытым_вопросам.md`;
  полный перечень несделанного — `docs/Что_осталось_сделать.md`.

Наличие поля в системе не означает, что внешняя система уже подключена.

# CRM ОР ПСД — АО «Казтелерадио»

Приём и обработка заявок на выдачу технических условий, разработку проектно-сметной
документации и выполнение строительно-монтажных работ; архив актов; контроль сроков
и показатели загрузки.

Система реализует действующий **Регламент оказания услуг ОРПСД-Р-01 ред. 2**: нормативы
этапов, условия переходов и правила автоматизации хранятся со ссылками на пункты и
проверяются на сервере. Обойти условие Регламента, обратившись к API напрямую, нельзя.

---

## Состав

| Каталог | Назначение |
|---|---|
| `src/domain/` | Предметная область: исчисление сроков, проверка заявки, расчёт стоимости |
| `src/process/` | Этапы, условия переходов, движок, правила автоматизации, показатели |
| `src/db/` | Схема PostgreSQL, миграции, доступ к данным |
| `src/server/` | HTTP-слой, аутентификация, права, API |
| `design/` | Дизайн-прототип интерфейса (открывается как обычная страница) |
| `tests/` | Тесты: правила Регламента, права, вход, маршрутизация |
| `deploy/` | Конфигурация обратного прокси |

---

## Требования к серверу

- Linux, **Node.js 22.6+** и **PostgreSQL 16+**;
- nginx как обратный прокси;
- доменное имя и TLS-сертификат;
- корпоративный провайдер OIDC (Keycloak, ADFS, Entra ID и т. п.);
- исходящий доступ к реестру npm на время установки.

**Docker не обязателен.** Приложение — обычный процесс Node.js, работающий с
PostgreSQL. Ниже два пути установки: без контейнеров (systemd) и через Docker
Compose. Они равноценны, выбирайте привычный для вашей ИТ-службы.

Все данные остаются на сервере Общества. Персональные данные и коммерческая тайна
(реестр АМС, загрузка, арендаторы) за пределы контура не передаются.

## Переменные окружения

Настройки задаются в файле `.env` (копируется из `.env.example`, в репозиторий
не коммитится). Обязательные:

| Переменная | Как получить |
|---|---|
| `APP_ORIGIN` | внешний адрес системы, например `https://crm.example.kz` |
| `SERVER_NAME` | домен без схемы, например `crm.example.kz` |
| `DATABASE_URL` | строка подключения; нужна при установке без Docker |
| `PGPASSWORD` | пароль базы: `openssl rand -base64 24` (используется в Compose) |
| `AUTH_PROXY_SHARED_SECRET` | `openssl rand -hex 32` — не короче 32 символов |
| `OIDC_ISSUER_URL`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET` | у администратора учётных записей |
| `OIDC_COOKIE_SECRET` | `openssl rand -base64 32 \| head -c 32` |
| `BOOTSTRAP_ADMIN_EMAIL` | рабочая почта первого администратора ДИТ |

## Установка без Docker (systemd)

### 1. Подготовить сервер

```bash
sudo apt update
sudo apt install -y nodejs npm postgresql nginx
node --version     # должно быть 22.6 или новее
```

Если в репозитории дистрибутива Node.js старее 22.6, поставьте из NodeSource
либо распакуйте официальную сборку в `/usr/local`.

### 2. Создать пользователя и базу

```bash
sudo adduser --system --group --home /opt/qtr-crm qtrcrm

sudo -u postgres psql <<'SQL'
CREATE USER qtr WITH PASSWORD 'задайте-пароль';
CREATE DATABASE qtr_crm OWNER qtr;
SQL
```

### 3. Забрать код

```bash
sudo git clone <адрес-репозитория> /opt/qtr-crm
sudo chown -R qtrcrm:qtrcrm /opt/qtr-crm
cd /opt/qtr-crm
sudo -u qtrcrm npm ci --omit=dev
```

### 4. Настроить

```bash
sudo -u qtrcrm cp .env.example .env
sudo -u qtrcrm nano .env
sudo chmod 600 .env
```

Для установки без Docker нужна строка подключения целиком:

```
DATABASE_URL=postgres://qtr:пароль@localhost:5432/qtr_crm
```

### 5. Применить миграции и запустить службу

```bash
sudo -u qtrcrm npm run migrate

sudo cp deploy/qtr-crm.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now qtr-crm
systemctl status qtr-crm
```

### 6. Настроить nginx и вход

Установите oauth2-proxy (пакетом либо бинарником в `/usr/local/bin`) и запустите
его на `127.0.0.1:4180` с параметрами вашего провайдера OIDC. Затем:

```bash
sudo cp deploy/nginx-site.conf /etc/nginx/sites-available/qtr-crm
sudo nano /etc/nginx/sites-available/qtr-crm   # домен и AUTH_PROXY_SHARED_SECRET
sudo ln -s /etc/nginx/sites-available/qtr-crm /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
```

Проверка:

```bash
curl -fsS https://<домен>/api/v1/health
```

### Обновление

```bash
cd /opt/qtr-crm
sudo -u qtrcrm git pull
sudo -u qtrcrm npm ci --omit=dev
sudo -u qtrcrm npm run migrate
sudo systemctl restart qtr-crm
```

## Установка через Docker Compose

Тот же результат одной командой: база, приложение, oauth2-proxy и nginx
поднимаются вместе с уже связанными сетями. Требуется Docker 24+ и Compose v2.

### 1. Забрать код на сервер

```bash
git clone <адрес-репозитория> /opt/qtr-crm
cd /opt/qtr-crm
```

### 2. Заполнить настройки

```bash
cp .env.example .env
```

Значения — в разделе «Переменные окружения» ниже.

### 3. Положить сертификаты

```bash
mkdir -p deploy/certs
cp /путь/fullchain.pem deploy/certs/
cp /путь/privkey.pem  deploy/certs/
chmod 600 deploy/certs/privkey.pem
```

### 4. Запустить

```bash
docker compose up -d --build
docker compose exec app npm run migrate
```

Проверка:

```bash
curl -fsS https://$SERVER_NAME/api/v1/health
```

### 5. Обновление

```bash
cd /opt/qtr-crm
git pull
docker compose up -d --build
docker compose exec app npm run migrate
```

## Первый вход (любой способ установки)

Откройте `https://<домен>/` и войдите под учётной записью, указанной в
`BOOTSTRAP_ADMIN_EMAIL`. Она получит роль ДИТ, если администраторов ещё нет.
Дальше роли назначаются вручную — самопроизвольной выдачи прав не происходит.

Демонстрационные справочники (филиалы, объекты, прейскурант) — по желанию:

```bash
npm run seed:demo                        # без Docker
docker compose exec app npm run seed:demo  # в контейнерах
```

## Миграции и откат

Миграции повторно не применяются: каждый файл отмечается контрольной суммой.
Попытка изменить уже применённый файл прерывается с ошибкой — вместо правки
добавляйте новый файл. Исключение — файл конфигурации процесса `002_config.sql`:
он идемпотентен и переприменяется, когда меняются этапы или правила.

Откат кода:

```bash
git checkout <предыдущий-тег>
sudo systemctl restart qtr-crm        # либо docker compose up -d --build
```

Откат кода не откатывает схему базы. Перед обновлением снимайте резервную копию —
это единственный надёжный путь назад.

## Локальная разработка

```bash
npm ci
export DATABASE_URL=postgres://qtr:пароль@localhost:5432/qtr_crm
npm run migrate
```

Без корпоративного входа:

```bash
SSO_ENABLED=false DEV_LOGIN_EMAIL=you@qtr.kz npm run dev
```

Режим разработки включается только при `SSO_ENABLED=false`; при включённом входе
переменная `DEV_LOGIN_EMAIL` игнорируется.

## Как устроен вход

Внешний доступ идёт через nginx. Он проверяет сессию в oauth2-proxy, а приложению
передаёт проверенную личность заголовками `X-QTR-User-*` вместе с общим секретом
`AUTH_PROXY_SHARED_SECRET`.

Приложение доверяет этим заголовкам **только** при совпадении секрета, сравнение
идёт за постоянное время. Поэтому:

- порт приложения наружу не публикуется: при установке через systemd оно слушает
  только `127.0.0.1`, в Compose сеть `backend` помечена `internal`;
- прокси обязан затирать заголовки `X-QTR-*`, пришедшие снаружи — в поставляемой
  конфигурации это сделано;
- при пустом или коротком секрете приложение не запускается.

Учётная запись закрепляется за первым вошедшим субъектом OIDC. Попытка войти под
тем же адресом с другим субъектом отклоняется.

## API

Базовый префикс `/api/v1`. Ответы — JSON, ошибки содержат `code`, а нарушения
Регламента — список `failures` со ссылками на пункты.

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/health` | Проверка доступности (без входа) |
| `GET` | `/config` | Этапы, переходы, правила, словари |
| `GET` | `/me` | Текущий пользователь, роли и права |
| `GET` | `/requests` | Список заявок в пределах прав |
| `POST` | `/requests` | Подача заявки или сохранение черновика |
| `GET` | `/requests/:id` | Карточка: услуги, замечания, история, доступные переходы |
| `POST` | `/requests/:id/transition` | Переход по этапу — единственный способ сменить этап |
| `POST` | `/requests/:id/tv` | Фиксация оценки ТВ с версией мастер-файла (п. 16.5) |
| `POST` | `/requests/:id/remarks` | Возврат на доработку с перечнем замечаний (ТЗ №11) |
| `GET` | `/board` | Доска: колонки-этапы и карточки |
| `GET` | `/metrics` | Узкие места: медиана против норматива, разбивка по сторонам |
| `GET` | `/facilities`, `/tariffs` | Справочники объектов и прейскуранта |

Пример перехода:

```bash
curl -X POST https://$SERVER_NAME/api/v1/requests/$ID/transition \
  -H 'Content-Type: application/json' \
  -d '{"to":"offer","version":3}'
```

Если условия Регламента не выполнены, вернётся `422`:

```json
{
  "code": "regulation_violation",
  "error": "Техническая возможность не подтверждена (п. 16.3)",
  "failures": [
    { "code": "tv_not_confirmed", "message": "…", "regulationRef": "п. 16.3" }
  ]
}
```

## Резервное копирование

```bash
docker compose exec db pg_dump -U qtr -Fc qtr_crm > backups/qtr_$(date +%F).dump
```

Восстановление на чистую базу:

```bash
docker compose exec -T db pg_restore -U qtr -d qtr_crm --clean --if-exists < backups/qtr_2026-09-22.dump
```

Рекомендуется схема 3-2-1: ежедневная копия, еженедельная полная, хранение копий
в пределах Республики Казахстан, ежеквартальная проверка восстановления.

## Проверка

```bash
npm test
```

Покрыто: исчисление сроков в рабочих и календарных днях, проверка заявки,
расчёт стоимости суммой позиций, условия переходов по Регламенту, эскалация,
показатели узких мест, вход через доверенные заголовки, ролевая модель,
маршрутизация.

**Что тестами не покрыто и проверяется на целевом сервере:** сборка и запуск
контейнеров, работа nginx и TLS, настоящий корпоративный OIDC, применение
миграций на рабочей базе, нагрузка при фактическом числе пользователей.

## Границы текущего объёма

Реализовано: заявки на ТУ/ПСД/СМР с несколькими услугами в одной заявке, оценка
технической возможности с фиксацией версии реестра, этапы и сроки Регламента,
эскалация, замечания к полям, архив актов, показатели узких мест, журнал действий.

Требуют отдельного внедрения:

- обмен с 1С и ИС ЭСФ (счета, АВР, ЭСФ ведутся реквизитами вручную);
- рассылка уведомлений по почте (подсистема спроектирована, отправка не подключена);
- электронная подпись: отметка «завизировано» подписью не является;
- модуль СУА «Портал допусков» — закладывается архитектурно, реализуется отдельно;
- антивирусная проверка вложений.

Наличие поля в системе не означает, что внешняя система уже подключена.
